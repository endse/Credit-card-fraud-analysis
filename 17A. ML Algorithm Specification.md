# 17A. ML Algorithm Specification

## 17A.1 MVP ML Strategy

The MVP shall use a **hybrid machine-learning architecture**:

```text
                    Transaction
                         │
                         ▼
                Feature Engineering
                         │
              ┌──────────┼──────────┐
              │          │          │
              ▼          ▼          ▼
         Supervised   Anomaly    Behavioral
            ML       Detection    Features
              │          │          │
              └──────────┼──────────┘
                         ▼
                  Fraud Scoring
                         │
                         ▼
                 Decision Engine
```

The primary supervised model shall be **XGBoost or LightGBM**, selected through benchmark evaluation on the project's validation dataset.

The MVP shall also maintain a **Logistic Regression baseline** to ensure the production model provides measurable improvement over a simple, interpretable classifier.

An **Isolation Forest** model may be used as a complementary anomaly detector for previously unseen transaction patterns.

---

# 17A.2 Algorithm Selection

## Primary Model — Gradient Boosted Trees

Candidate:

```text
XGBoost
OR
LightGBM
```

The final algorithm shall be selected using validation performance, latency, calibration, and explainability.

Why this model class:

- handles tabular transaction data effectively
- captures nonlinear relationships
- handles feature interactions
- works well with heterogeneous numerical/categorical-derived features
- supports class weighting
- provides feature importance
- supports relatively low-latency inference

Example relationship:

```text
High Amount
     +
New Device
     +
Unusual Country
     +
High Transaction Velocity
     ↓
High Fraud Probability
```

A tree-based model can capture interactions between these signals without requiring the engineering team to manually encode every interaction.

# 17A.6 Preventing Data Leakage

This is a mandatory ML requirement.

Training features must represent only information that would have been available **at the time the transaction was evaluated**.

For example, this must not happen:

```text
Transaction
   ↓
Fraud confirmed 3 days later
   ↓
Fraud label accidentally used in historical feature
   ↓
Model training
```

Instead:

```text
Transaction at T
      ↓
Only information available ≤ T
      ↓
Feature generation
      ↓
Model
```

Train/validation/test splitting should be **time-aware** rather than purely random where transaction chronology matters.

---

# 17A.7 Class Imbalance Handling

Because fraudulent transactions may be much rarer than legitimate transactions, the system shall explicitly handle imbalance.

Candidate techniques:

```text
Class Weights
Weighted Loss
Under-sampling
Over-sampling
SMOTE (where validated)
Threshold Optimization
```

The preferred initial approach should be **class weighting plus decision-threshold optimization**.

Synthetic data techniques should not be accepted solely because they increase offline metrics.

---

# 17A.8 Training Pipeline

The training workflow shall be:

```text
Historical Transactions
        ↓
Data Quality Checks
        ↓
Time-Based Split
        ↓
Feature Engineering
        ↓
Class-Balance Strategy
        ↓
Baseline Training
        ↓
XGBoost/LightGBM Training
        ↓
Hyperparameter Search
        ↓
Probability Calibration
        ↓
Threshold Optimization
        ↓
Evaluation
        ↓
Explainability Analysis
        ↓
Model Registration
        ↓
Approval
        ↓
Deployment
```

Recommended split:

```text
Training      70%
Validation    15%
Test          15%
```

For production-like evaluation, the split should be chronological, for example:

```text
Older transactions → Training
Later transactions → Validation
Newest transactions → Test
```

The precise proportions may be adjusted based on dataset size and fraud-event availability.


Hyperparameter optimization may use:


A possible optimization objective:

```text

    PR-AUC
    +

    +

    false positive rate ≤ configured threshold
```

# 17A.10 Probability Calibration

The raw output of the classifier should not automatically be treated as a true probability.

The model should undergo calibration using an appropriate method such as:

```text
Platt Scaling
OR
Isotonic Regression
```

After calibration:

```text
Model Output
     ↓
Calibration
     ↓
Fraud Probability
```

The system must distinguish:

```text
Raw Model Score
Fraud Probability
Business Risk Score
Decision
```

These are separate quantities.

---

# 17A.11 Risk Score Conversion

The calibrated fraud probability may be converted to a standardized risk score.

Example:

```text
fraud_probability = 0.91

risk_score =
round(fraud_probability × 100)

risk_score = 91
```

However, business rules may further modify the final risk score.

Example:

```text
ML Score              = 91
Behavior Score        = 85
Rule Score             = 100
Merchant Risk          = 60

Final Risk Score       = 92
```

The exact aggregation formula shall be version-controlled.

# 17A.12 Anomaly Detection

The MVP may include:

```text
Isolation Forest
```

as a secondary model.

Purpose:

```text
Known Fraud
   ↓
Supervised Model

Unknown / Novel Behavior
   ↓
Anomaly Detector
```

The anomaly detector should not automatically block transactions solely because they are anomalous unless explicitly approved by the business decision policy.

Its primary role in the MVP is:

```text
Anomaly Score
      ↓
Additional Risk Signal
```

# 17A.14 ML Acceptance Thresholds

The MVP model shall meet:

```text
Precision       ≥ 80%
Recall          ≥ 70%
F1 Score        ≥ 75%
ROC-AUC         ≥ 0.90
PR-AUC          ≥ 0.70
False Positive  ≤ 5%
```

Additionally:

```text
Prediction Coverage ≥ 99.5%
```

These metrics must be calculated on an untouched, time-separated test set.

---

# 17A.15 Threshold Optimization

The probability threshold must not automatically be fixed at:

```text
0.50
```

Instead, evaluate multiple thresholds:

```text
0.20
0.25
0.30
0.35
0.40
0.45
0.50
0.55
0.60
0.65
0.70
0.75
0.80
```

For each threshold calculate:

```text
Precision
Recall
F1
False Positive Rate
False Negative Rate
Fraud Captured
Transactions Blocked
```

The selected threshold should minimize the expected business cost.

Example:

```text
Cost(False Negative)
        >
Cost(False Positive)
```

will generally favor higher recall.

But the actual threshold must be determined from the project's documented fraud-loss and customer-friction assumptions.

# 17A.16 Confusion Matrix

Every model release must generate:

```text
                 ACTUAL
             Fraud     Legit
          ┌──────────┬──────────┐
Pred Fraud│    TP    │    FP    │
          ├──────────┼──────────┤
Pred Legit│    FN    │    TN    │
          └──────────┴──────────┘
```

Where:

```text
TP = correctly detected fraud
FP = legitimate transaction incorrectly flagged
FN = fraud that was missed
TN = correctly accepted legitimate transaction
```

The confusion matrix must be included in every model evaluation report.

---

# 17A.17 Explainability

For each high-risk prediction, the system should return the most influential features.

Example:

```text
Fraud Probability: 0.91

Top Signals:

1. amount_deviation_ratio = 8.2
2. is_new_device = true
3. is_new_country = true
4. txn_count_15m = 9
5. merchant_risk_score = 78
```

SHAP may be used for tree-based model explanations.

The explanation service must use the exact model version that generated the prediction.

# 17A.19 Java ↔ Python ML Integration

The architecture shall be:

```text

          │
          ▼
Feature Service
          │
          ▼
Python ML API
          │
          ▼
Model Prediction
          │
          ▼
Java Decision Engine
          │
          ▼
APPROVE / REVIEW / CHALLENGE / BLOCK
```

Java should own the business decision.

Python should primarily own:

```text
Feature preprocessing where appropriate
Model inference
ML explanations
Model metadata
```

This separation prevents business rules from becoming embedded inside the ML model.

# 17A.21 Model Promotion

Models must pass:

```text
TRAINING
   ↓
VALIDATION
   ↓
CANDIDATE
   ↓
STAGING
   ↓
SHADOW
   ↓
PRODUCTION
```

A model should not be promoted directly from training to production.

In **shadow mode**, the candidate model generates predictions without affecting transaction decisions.

This enables comparison against the currently deployed model.

---

# 17A.22 Model Retraining

The MVP should support controlled retraining.

Possible trigger:

```text
New confirmed fraud labels
+
Sufficient new transactions
+
Model performance degradation
+
Significant data drift
```

Retraining should not automatically deploy the new model.

Required sequence:

```text
Retrain
 ↓
Evaluate
 ↓
Compare with Production
 ↓
Approve
 ↓
Deploy
```

```text

    ↓

    ↓
```


This gives the project a practical ML architecture without prematurely introducing deep learning or graph neural networks.
